## ทำไมเฟสนี้

จาก[[Chata Progress 2026-08-29|การประเมิน]]: **หมอดูยังเอาเงินออกไม่ได้เลย** วงจรเงินจบที่
`payable_coin` โตขึ้นเฉย ๆ — ไม่ใช่ฟีเจอร์ที่ขาด แต่คือด้านที่หายไปครึ่งหนึ่งของตลาด
user เคาะว่า **ปิด payout ก่อน แล้วค่อยทำ call** ซึ่งถูก เพราะ call ก็ปลายทางเดียวกัน

## ข้อตัดสินใจที่เคาะแล้ว (จากการซัก 2 รอบ)

### payout

| เรื่อง | เคาะว่า |
|---|---|
| admin ทำงานผ่านอะไร | Supabase Studio **แต่บังคับเรียกผ่าน RPC ที่มี audit** ห้าม `update` ดิบ · ยังไม่สร้าง admin app |
| เงินออกยังไง | **โอนมือ** + เลขอ้างอิง · PSP payout ไทยต้องจดบริษัท + KYB กินเวลาเป็นเดือน |
| อัตราแลก | **1 coin = 1 บาท** (ผู้ใช้ซื้อที่ ~1 บาท/coin, หมอดูได้ 70%) |
| ค่าธรรมเนียม / ขั้นต่ำ / hold | 0 / 500 coin / **7 วัน** — ทุกค่าอยู่ใน `app_config` |
| ภาษีหัก ณ ที่จ่าย | **ใส่ฟิลด์ไว้แต่ตั้ง 0** รอนักบัญชี (40(2) vs 40(8)) — ไม่เดาตัวเลขภาษีให้ user |
| KYC | **บังคับ verified ก่อนถอน** ตรวจผ่าน `seer_document` ที่เฟส 2 ทำไว้ เพิ่มชนิด "หน้าสมุดบัญชี" |

### call

| เรื่อง | เคาะว่า |
|---|---|
| คิดเงิน | **แพ็กเหมา + ต่อเวลา** ไม่ใช่มิเตอร์รายนาที · แต่โชว์ราคาเป็นเหรียญ/นาทีที่หน้ารายการ |
| เสียงเรียกเข้า | **v1 ดังเฉพาะตอนเปิดแอป** ยังไม่ทำ CallKit/PushKit |
| media | **LiveKit Cloud · เสียงอย่างเดียวก่อน** วิดีโอเปิดทีหลังด้วย flag |
| สถานะออนไลน์ | Presence เป็นตัวตัดสิน + projection ลงคอลัมน์ให้ filter ด้วย SQL ได้ |
| หมอดูออฟไลน์ | ยังไม่ทำ Book Queue → fallback ไปส่งคำถามข้อความ |

## เหตุผลสำคัญที่ควรจำ

**ทำไมไม่ใช้มิเตอร์รายนาทีทั้งที่คู่แข่งใช้** — (1) escrow ทำได้จริงเมื่อรู้ยอดตั้งแต่ต้น
(2) มิเตอร์ต้องหักเงินระหว่างสาย ถ้าหักไม่สำเร็จตอนเน็ตสะดุดจะเถียงกันไม่จบว่าคุยไปกี่นาที
(3) ผู้ใช้ที่เหรียญหมดกลางสายโดนตัดสายทันที แย่กว่ารู้ตั้งแต่ต้นว่าได้กี่นาที

**ทำไม "Online = เปิดแอปอยู่" ถึงเป็นคำตอบที่ดี ไม่ใช่แค่ข้อจำกัด** — เราไม่มีบัญชี Apple Developer
เลยทำ VoIP push ไม่ได้ แต่โมเดลนี้กลับ**ตรงกับความจริง**: หมอดูที่ไม่ได้เปิดแอปกดรับสายไม่ได้อยู่แล้ว
ข้อจำกัดกับดีไซน์ที่ถูกบังเอิญตรงกัน

**hold 7 วันไม่ได้ปิดความเสี่ยง Apple 90 วัน** — แต่ตัดรูปแบบฉ้อโกงที่พบบ่อยสุด
(ซื้อ-ใช้-ถอน-ขอคืนภายในไม่กี่วัน) ส่วนที่เหลือ**ยอมรับความเสี่ยงใน v1** อย่างรู้ตัว
ทางแก้เต็มรูปคือ `moderation_action(debt_flag)` ซึ่งยังไม่มีตาราง

## บทเรียนจาก ticket 01

**เทสที่เขียวด้วยเหตุผลผิด — เจออีกสองข้อในรอบแดงเดียว**
- "หมอดูเขียนรายได้เองไม่ได้" เขียนไว้ว่ารับ error อะไรก็ได้ → ตอนตารางยังไม่มี ได้ `PGRST205`
  ก็เขียว ทั้งที่ยังไม่ได้พิสูจน์เรื่องสิทธิ์เลย → บังคับ `42501` เท่านั้น
- "คนอื่นอ่านไม่เห็น" ใช้ `jq length` ซึ่งนับ key ของ error object ได้ 4 → บังคับว่าต้องเป็นอาเรย์ว่าง

**ต่อยอดจากบทเรียนเดิม: รอบแดงต้องอ่านว่า "แดงเพราะอะไร" และ "เขียวเพราะอะไร" ทุกข้อ
ไม่ใช่ดูแค่จำนวนที่ผ่าน** — ข้อที่เขียวตั้งแต่รอบแดงคือสัญญาณเตือนเสมอ

**pattern matching หลวมทำให้อ่านผลผิด — ครั้งที่สามแล้ว**
`jq '// empty'` พังกับ boolean · `grep -i FAIL` ไปโดน `"failed": 0` ใน JSON ·
คราวนี้ `grep '^psql:'` ไปโดนบรรทัด NOTICE ที่ psql ขึ้นต้นให้เอง
→ **ตรวจที่ระดับความรุนแรงจริง `: (ERROR|WARNING|FATAL):` ไม่ใช่ substring ลอย ๆ**

**`internal_post_ledger` คืน transaction id อยู่แล้ว แต่ของเดิมใช้ `perform` ทิ้งไป**
พอต้องการ projection ที่โยงกลับไปหาหลักฐานถึงได้รู้ว่ามีของให้ใช้อยู่แล้ว

**backfill ต้องถอดตัวเลขกลับจากของจริง ไม่ใช่คำนวณใหม่** — ถ้า backfill คิด
`revenue_share_bps` จากอัตราปัจจุบัน รายการเก่าทั้งหมดจะเพี้ยนทันทีที่มีใครเปลี่ยนอัตรา
จึงถอดกลับจากจำนวนเหรียญที่ post ไว้จริงใน ledger

### ที่เจอเพราะอะไร

เพิ่งทำ `scripts/test-sql.sh` ขึ้นมา — **ชั้น SQL ไม่เคยมี runner เลย** ที่ผ่านมาตรวจด้วยมือ
และ pattern ที่ใช้ (`^(ERROR|WARNING)`) ไม่แมตช์รูปแบบจริงของ psql ซึ่งคือ
`psql:<stdin>:173: ERROR:` → **รายงานว่าผ่านทั้งที่ล้มจริง**

นี่คือ pattern matching หลวม**ในทิศตรงข้าม**กับสองครั้งก่อน: คราวก่อนทำให้ของที่ผ่านขึ้นแดง
คราวนี้ทำให้ของที่ล้ม**เงียบ** — อันหลังอันตรายกว่ามาก

→ แก้ที่ต้นเหตุแล้ว: มี runner จริง ตัดสินด้วย `: (ERROR|WARNING|FATAL):` และเขียนเหตุผล
ไว้หัวไฟล์ว่าทำไมห้ามใช้ pattern อื่น · พร้อมไล่แก้ในชุด REST อีก 4 จุดที่เป็นบั๊กชนิดเดียวกัน

· ผลข้างเคียงที่ยอมรับ: ฟอร์มเติมเลขเดิมให้ไม่ได้ ต้องพิมพ์ใหม่ทุกครั้ง — ถูกแล้วสำหรับข้อมูลระดับนี้

**แยก `admin_reveal_payout_account` ออกจากคำสั่งตรวจ** เพราะ "การเปิดดูเลขบัญชี"
ต้องนับได้เอง ไม่ใช่ผลข้างเคียงของอย่างอื่น — แอดมินที่จะโอนเงินต้องเปิดดูอยู่แล้ว
และทุกครั้งต้องทิ้งร่องรอย · เทสตรวจว่า**จำนวนแถว audit เพิ่มขึ้นจริง** ไม่ใช่แค่มีแถวอยู่

**แก้บัญชี = soft delete + ออกแถวใหม่ ไม่ใช่ update ทับ** เพราะ `payout_request` ที่จ่ายไปแล้ว
อ้างถึงบัญชีปลายทาง ณ ตอนนั้น ถ้าแก้ทับ ประวัติการโอนจะชี้ไปบัญชีผิด — เรื่องนี้จะเจอตอน
ticket 04 ถ้าไม่ทำตั้งแต่ตอนนี้

**แก้บัญชีแล้วสถานะกลับเป็น pending เสมอ** — ถ้าปล่อยให้ยัง verified อยู่ด้วยเลขใหม่
ที่ยังไม่มีใครดู = ช่องโอนเงินเข้าบัญชีที่ไม่เคยผ่าน KYC


## ticket 03 — บทเรียน (2026-08-29)

**definer view เรียกฟังก์ชันที่ revoke ไว้ไม่ได้** — `v_my_payout_summary` พังด้วย
`permission denied for function get_config` · เพราะ **definer view ใช้สิทธิ์เจ้าของกับ*ตาราง*
แต่การเรียก*ฟังก์ชัน* ยังเช็คสิทธิ์ของผู้เรียก** → view ที่อ่าน config ต้องอ่าน `app_config`
ตรง ๆ ไม่ผ่าน `get_config` ที่ revoke จาก authenticated ไว้
(RPC เรียก `get_config` ได้ปกติ เพราะ definer function เช็คด้วยสิทธิ์ของเจ้าของฟังก์ชัน)

**เทส "ขอซ้อน" ผ่านด้วยเหตุผลผิด — ครั้งที่สามของ pattern นี้**
ขอถอนไปทั้งหมดแล้ว รอบสองเลยแดงเพราะเงินหมด ไม่ใช่เพราะตัวกันถอนซ้อน
**unique partial index ที่เป็นตัวกันจริงไม่เคยถูกทดสอบเลย**
→ แก้เป็นขอแค่ขั้นต่ำ เหลือไว้ 1000 เหรียญ แล้วบังคับว่าต้องแดงด้วย `payout_already_pending`
เท่านั้น พร้อมเช็คก่อนว่ายังเหลือเงินพอจริง ไม่งั้นให้แดง

**สรุปรูปแบบที่เจอซ้ำ ๆ ทั้งวัน:** เทสที่เขียวเพราะระบบยังไม่มีของ / เพราะเงินหมด /
เพราะค่าว่างกลายเป็น 0 — **ทุกครั้งที่เขียนเทสเรื่อง "ต้องถูกปฏิเสธ" ต้องถามว่า
"ถูกปฏิเสธด้วยเหตุผลที่เราตั้งใจทดสอบจริงไหม" ไม่ใช่แค่ว่ามันแดง**

## หลักการที่ตกผลึกจาก payout

**ยอดถอนได้ = `min(ยอดค้างจ่ายจริง, รายได้ที่สุกแล้ว − ที่ขอไปแล้ว)`** — สองเงื่อนไข
คนละเรื่องและต้องผ่านทั้งคู่

**เลขที่ผู้ใช้เห็นกับเลขที่บันทึกต้องมาจากฟังก์ชันเดียวกัน** (`internal_payout_quote`)
ไม่ใช่คำนวณคนละที่แล้วหวังว่าจะตรงกัน

**ตัวกันเรื่องเงินต้องอยู่ในฐาน ไม่ใช่ในโค้ด** — โค้ดที่เช็คก่อน insert แพ้ race เสมอ
ใช้ unique partial index แล้วดัก `unique_violation` แปลงเป็นข้อความที่อ่านรู้เรื่อง


## ticket 04 + เรื่องใหญ่ที่เจอตอน user ถามว่า "เทสหมดแล้วยัง" (2026-08-29)

**payout ครบวงจรแล้ว** — ขอ → อนุมัติ → โอนจริง (บังคับเลขอ้างอิง) และทางที่ไม่ได้จ่าย
คือ ปฏิเสธ/ยกเลิก ซึ่งคืนเงินด้วย **reversing entry** ที่ชี้ `reversal_of` กลับต้นฉบับ
· การจ่ายจริง**ไม่แตะ ledger เลย** เพราะเหรียญออกไปตั้งแต่ตอนขอ

### 🔴 เทสข้ามตัวเองเงียบ ๆ — เจออีกครั้ง คนละที่กับคราวก่อน

`testSeerCanCancel...` ใช้ `XCTSkipUnless` แล้ว**ข้ามตัวเองทุกรอบที่สอง** โดย `test-ios.sh`
ยังขึ้น `TEST SUCCEEDED` เพราะ grep ไม่ได้ดูคำว่า skipped เลย

**นี่คือ failure mode เดียวกับตอนชุด REST ชี้ cloud แล้วข้ามทั้งชุดเงียบ ๆ**
ต่างที่คราวนี้เกิดในชั้น iOS และเกิดจากเงื่อนไขในตัวเทสเอง ไม่ใช่ตัวเช็คสภาพแวดล้อม

แก้สามชั้น:
1. `test-ios.sh` **ดักตัวที่ข้ามแล้ว exit 1** (ปลดล็อกด้วย `ALLOW_SKIPPED=1`)
2. **เอา `XCTSkipUnless` ออก** → เงื่อนไขไม่พร้อมก็ต้องพิสูจน์ขาตรงข้าม
   ("ขอถอนไม่สำเร็จและเหรียญไม่ขยับ") ไม่ใช่ไม่ทำอะไรเลย
3. **fixture กำหนดสถานะตั้งต้นให้ครบ** — บัญชีที่ตรวจแล้ว + รายได้ที่พ้นระยะรอ 2000 เหรียญ
   + เคลียร์คำขอถอนที่ค้าง

### บทเรียนที่แรงที่สุดของรอบนี้

**"เทสเขียว" ไม่พอ ต้องพิสูจน์ว่า "ขาที่ตั้งใจทดสอบถูกเดินจริง"**
วิธีที่ใช้: **นับแถวในฐานก่อน/หลังรันเทส** — คำขอที่ถูกยกเลิกต้องเพิ่มขึ้น 1 ทุกครั้งที่รันชุด iOS
ถ้าไม่เพิ่ม แปลว่าเทสไปเข้าขาสำรองหรือข้ามตัวเอง · ตรวจแบบนี้แล้วเจอว่า **แก้สองรอบแรก
ยังไม่พอ** ทั้งที่ขึ้น TEST SUCCEEDED ทุกรอบ

**เทส integration ที่ใช้ fixture ร่วมกันจะพันกันเองเสมอ** — เทสผูกบัญชีธนาคารรีเซ็ตสถานะ
เป็น "รอตรวจ" (พฤติกรรมที่ถูกต้อง) แล้วทำให้เทสถอนเงินที่รันทีหลังเข้าขาสำรอง
· XCTest รันตามลำดับตัวอักษร ซึ่งเป็นสัญญาที่เปราะมาก → ทางแก้ที่ถูกคือ**ให้ fixture
เป็นเจ้าของสถานะตั้งต้น** ไม่ใช่หวังพึ่งลำดับ

**invariant ที่เคยจริง เลิกจริงได้เมื่อ domain โตขึ้น** — "ผลรวมรายได้ = ยอดค้างจ่าย"
จริงเฉพาะตอนยังไม่มีการถอน พอมี payout ต้องเป็น "รายได้ทั้งหมด − ที่ถอนออกไปแล้ว = ยอดค้างจ่าย"
