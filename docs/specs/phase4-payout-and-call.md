# เฟส 4 — ปิดวงจรเงิน (payout) แล้วต่อด้วยโทรคุยดูดวง (call)

## Problem Statement

**ฝั่งหมอดู — เงินเข้าแล้วออกไม่ได้**

ตอนนี้หมอดูปิดงานแล้วเห็นตัวเลข "ยอดค้างจ่าย" เพิ่มขึ้นจริงบนหน้าจอ แต่**ไม่มีทางเอาเงินนั้นออกมาได้เลย**
ไม่มีที่ให้กรอกเลขบัญชี ไม่มีปุ่มขอถอน ไม่มีใครโอนให้ ยอดค้างจ่ายจึงเป็นแค่ตัวเลขที่โตขึ้นเรื่อย ๆ
ในมุมหมอดูนี่ไม่ใช่ฟีเจอร์ที่ขาด แต่คือเหตุผลที่จะไม่มาใช้แพลตฟอร์มตั้งแต่แรก

**ฝั่งผู้ใช้ — อยากคุย ไม่อยากพิมพ์รอ**

ช่องทางเดียวที่มีคือส่งคำถามเป็นข้อความแล้วรอหมอดูตอบ ซึ่งอาจใช้เวลาเป็นชั่วโมง
คนที่กำลังเครียดและอยากได้คำตอบเดี๋ยวนี้ไม่มีทางเลือก — และการดูดวงส่วนใหญ่เป็นการสนทนา
ไม่ใช่การถาม-ตอบครั้งเดียว

## Solution

### ส่วนที่ 1 — payout

หมอดูกรอกบัญชีธนาคารของตัวเองในแอป อัปโหลดหน้าสมุดบัญชี แอดมินตรวจว่าชื่อตรงกับบัตรประชาชน
ที่เคยยื่นตอนสมัคร แล้วกดยืนยัน · หลังจากนั้นหมอดูกดขอถอนได้เมื่อยอดที่ "สุกแล้ว" ถึงขั้นต่ำ
ระบบกันเหรียญออกจากยอดค้างจ่ายทันทีตอนขอ (กันถอนซ้อน) แอดมินเห็นคิว โอนเงินจริงผ่านแอปธนาคาร
แล้วกดบันทึกเลขอ้างอิง · หมอดูเห็นสถานะทุกขั้นและประวัติการถอนย้อนหลัง

### ส่วนที่ 2 — call

ผู้ใช้เปิดหน้ารายชื่อหมอดูที่**กรองเฉพาะคนที่ออนไลน์อยู่ตอนนี้**ได้ เห็นราคาเป็นเหรียญ/นาที
เพื่อเทียบกันง่าย · กดเข้าโปรไฟล์ เห็นแพ็กที่หมอดูตั้งไว้ (เช่น 15 นาที 150 เหรียญ, 30 นาที 280 เหรียญ)
เลือกแพ็กแล้วกดโทร เหรียญถูกกันไว้ทันที · ฝั่งหมอดูมีสายเรียกเข้าพร้อมเสียงในแอป กดรับหรือปฏิเสธได้
· รับแล้วคุยกันด้วยเสียงผ่าน LiveKit · ใกล้หมดเวลาระบบเตือน ผู้ใช้ต่อเวลาเป็นก้อนได้
· วางสายแล้วเงินออกจาก escrow เข้ายอดค้างจ่ายของหมอดู ซึ่ง**เชื่อมกับส่วนที่ 1 ให้ถอนออกได้จริง**

## User Stories

### payout — ฝั่งหมอดู

1. As a หมอดู, I want ที่กรอกเลขบัญชีธนาคารของตัวเองในแอป, so that แพลตฟอร์มรู้ว่าจะโอนเงินไปไหน
2. As a หมอดู, I want เห็นเฉพาะเลขบัญชี 4 ตัวท้ายหลังบันทึกแล้ว, so that ถ้ามีคนแอบดูจอก็ไม่ได้เลขบัญชีเต็มไป
3. As a หมอดู, I want แก้บัญชีรับเงินได้, so that ย้ายธนาคารแล้วยังถอนได้
4. As a หมอดู, I want รู้ว่าบัญชีของฉันผ่านการตรวจแล้วหรือยัง, so that ไม่กดขอถอนแล้วโดนปฏิเสธโดยไม่รู้เหตุผล
5. As a หมอดู, I want รู้ว่าทำไมบัญชีถูกปฏิเสธ, so that แก้ให้ถูกแล้วยื่นใหม่ได้
6. As a หมอดู, I want เห็นยอดที่ถอนได้จริงแยกจากยอดค้างจ่ายทั้งหมด, so that ไม่เข้าใจผิดว่าถอนได้ทั้งก้อนทั้งที่บางส่วนยังไม่พ้นระยะรอ
7. As a หมอดู, I want รู้ว่ายอดที่ยังถอนไม่ได้จะถอนได้เมื่อไหร่, so that วางแผนการเงินของตัวเองได้
8. As a หมอดู, I want เห็นว่าถอนขั้นต่ำเท่าไหร่, so that ไม่กดแล้วโดนปฏิเสธ
9. As a หมอดู, I want เห็นว่าเหรียญที่ถอนจะได้เงินจริงกี่บาท ก่อนกดยืนยัน, so that ไม่เซอร์ไพรส์ตอนเงินเข้าบัญชี
10. As a หมอดู, I want เห็นค่าธรรมเนียมและภาษีที่ถูกหักแยกบรรทัด, so that ตรวจสอบได้และเอาไปทำบัญชีของตัวเองได้
11. As a หมอดู, I want กดขอถอนแล้วเห็นยอดค้างจ่ายลดลงทันที, so that รู้ว่าคำขอเข้าระบบแล้วจริง
12. As a หมอดู, I want ถูกห้ามขอถอนซ้อนขณะที่ยังมีคำขอค้างอยู่, so that ไม่เผลอถอนเกินที่มี
13. As a หมอดู, I want ยกเลิกคำขอถอนได้ตราบใดที่แอดมินยังไม่โอน, so that เปลี่ยนใจหรือแก้เลขบัญชีผิดได้
14. As a หมอดู, I want ได้เหรียญคืนครบเมื่อยกเลิกหรือถูกปฏิเสธ, so that ไม่มีเหรียญหายไประหว่างทาง
15. As a หมอดู, I want เห็นสถานะคำขอว่าอยู่ขั้นไหน (รอตรวจ / อนุมัติแล้ว / โอนแล้ว / ถูกปฏิเสธ), so that ไม่ต้องทักไปถาม

19. As a หมอดู, I want รู้เหตุผลเมื่อคำขอถูกปฏิเสธ, so that ไม่ต้องเดาว่าทำอะไรผิด

## Implementation Decisions

### ตัดสินใจร่วม

- **ทำ payout ให้จบก่อน แล้วค่อยเริ่ม call** — call ปลายทางคือ `seer_payable` ซึ่งถ้าถอนไม่ได้
  ก็ได้แค่ตัวเลขโตขึ้นอีกทางหนึ่ง การทำ payout ก่อนทำให้ call มีปลายทางจริงตั้งแต่วันแรก
- **ทุกตัวเลขเชิงนโยบายอยู่ใน `app_config`** ไม่ hardcode และไม่ต้อง migration เวลาปรับ
- ยึด schema ที่ออกแบบไว้แล้วใน `chata-database-design.md` §4.5 และ §4.9 เป็นหลัก
  ส่วนที่เบี่ยงจากเอกสารระบุไว้ชัดข้างล่าง

### payout — ตาราง

เพิ่ม 3 ตารางตาม §4.9: `seer_earning` · `payout_account` · `payout_request`

- **`seer_earning` ต้องมาก่อนทุกอย่าง** เพราะ hold period คำนวณจาก `created_at` ของมัน
  ตอนนี้ `internal_settle_question` โพสต์ ledger อย่างเดียว ไม่ได้เขียน projection นี้
  (คอมเมนต์ใน `20260826000009_rpc_consultation.sql` เขียนไว้เองว่ายกไปทีหลัง)
  → ต้องแก้ให้ settle เขียน `seer_earning` ในทรานแซกชันเดียวกัน และ **backfill ของเก่าจาก ledger**
- **`payout_request` กันถอนซ้อนด้วย unique partial index** บน `seer_id` เฉพาะสถานะ
  `requested`/`approved` ตามที่ §4.9.3 ระบุ
- เหรียญออกจาก `seer_payable` **ตอน `requested` ทันที** ไม่ใช่ตอน `paid` — ถ้าปฏิเสธหรือยกเลิก
  ทำ reversing entry คืน

### payout — เบี่ยงจากเอกสาร: ไม่เข้ารหัสเลขบัญชีด้วย pgsodium

§4.9.2 เขียนไว้ว่า `account_number_encrypted bytea` ผ่าน pgsodium/Vault
**แต่ Supabase ประกาศเลิกแนะนำ pgsodium และ Transparent Column Encryption แล้ว**
โดยให้เหตุผลว่าซับซ้อนเกินและตั้งค่าผิดได้ง่าย พร้อมระบุว่าโปรเจกต์ถูกเข้ารหัส at rest อยู่แล้ว

→ v1 เก็บเลขบัญชีเป็น `text` ในตารางที่ **RLS deny-all** เข้าถึงได้เฉพาะ service_role
   ผ่าน RPC ที่บันทึก `audit_log` ทุกครั้ง · client เห็นได้แค่ `account_number_last4` ผ่าน view
→ ถ้าภายหลังต้องการมากกว่านี้ ใช้ `pgcrypto` โดยเก็บ key ใน Supabase Vault (ทางที่ Supabase แนะนำแทน)
   ซึ่งเปลี่ยนได้โดยไม่กระทบ interface ของ RPC

### payout — RPC และ view

| ชื่อ | ใคร | ทำอะไร |
|---|---|---|
| `set_payout_account` | seer | บันทึก/แก้บัญชีรับเงิน รีเซ็ตสถานะกลับเป็น `pending` |
| `request_payout` | seer | ตรวจ KYC + ยอดสุก + ขั้นต่ำ → ล็อก wallet → โพสต์ ledger `payout` → สร้างคำขอ |
| `cancel_payout_request` | seer | ยกเลิกได้เฉพาะก่อนสถานะ `paid` → reversing entry |
| `admin_review_payout` | service_role | `approve` / `reject` / `mark_paid` พร้อมเหตุผลและเลขอ้างอิง |
| `v_my_payout_account` | seer | โชว์เฉพาะ last4 + สถานะ |
| `v_my_payout_history` | seer | ประวัติคำขอ |
| `v_my_earning_summary` | seer | ยอดถอนได้ / ยอดที่ยังรออยู่ / วันที่จะสุก |

- **แอดมินห้าม `update payout_request` ตรง ๆ** ทุกการเปลี่ยนสถานะต้องผ่าน `admin_review_payout`
  ซึ่งเขียน `audit_log` ให้เอง · แอดมินทำงานผ่าน Supabase Studio โดยรัน `select admin_review_payout(...)`
  (ยังไม่สร้าง admin app ในเฟสนี้)

### payout — ค่าตั้งต้นใน `app_config`

| key | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `payout.conversion_rate_micro` | `1000000` | satang ต่อ coin × 10⁶ → 1 coin = 1 บาท |
| `payout.fee_minor` | `0` | ค่าธรรมเนียมต่อคำขอ (satang) |
| `payout.withholding_bps` | `0` | ภาษีหัก ณ ที่จ่าย — **ตั้ง 0 ไว้ก่อน รอนักบัญชีเคาะ** |
| `payout.min_coin` | `500` | ขั้นต่ำต่อคำขอ |
| `payout.hold_days` | `7` | รายได้ต้องเก่ากว่านี้ถึงถอนได้ |

`hold_days` มีไว้กันเคสซื้อ-ใช้-ถอน-แล้วขอคืนเงินกับ Apple ภายในไม่กี่วัน ซึ่งเป็นรูปแบบฉ้อโกงที่พบบ่อยที่สุด
· ไม่ได้ปิดความเสี่ยง 90 วันของ Apple ทั้งหมด และ**ยอมรับความเสี่ยงส่วนที่เหลือใน v1**
(ทางแก้เต็มรูปคือ `moderation_action(debt_flag)` ซึ่งยังไม่มีตาราง — ไม่อยู่ในเฟสนี้)

### call — ตาราง

เพิ่ม 3 ตารางตาม §4.5: `call_transaction` · `call_extension` · `media_session`
บวกอีก 1 ตัวที่เอกสารยังไม่มี:

- **`seer_service_package`** — ลูกของ `seer_service` เก็บ `duration_seconds` + `price_coin` +
  `kind` (`base` | `extension`) · จำเป็นเพราะ `seer_service` เป็น `UNIQUE (seer_id, service_type_code)`
  ซึ่งมีราคาเดียวต่อบริการ แต่โจทย์คือหมอดูตั้งได้หลายแพ็ก · `call_transaction.base_duration_seconds`
  และ `call_extension.coin_amount` snapshot มาจากตารางนี้ ราคาเปลี่ยนทีหลังไม่กระทบสายที่จบไปแล้ว
- `seer_service.service_type_code` ปัจจุบัน CHECK ไว้แค่ `'chat_question'` → เพิ่ม `'voice_call'`
  พร้อมขยาย `service.price_bounds` ใน `app_config`
- **สถานะออนไลน์**: เพิ่ม `seer_profile.is_online` + `last_seen_at` เป็น **projection**
  ความจริงอยู่ที่ Realtime Presence · cron ปิดสถานะให้เมื่อ `last_seen_at` เงียบเกินกำหนด
  เหตุผลที่ต้องมีคอลัมน์: หน้ารายการต้องกรอง/เรียงด้วย SQL ซึ่ง Presence ล้วนทำไม่ได้

### call — คิดเงินแบบแพ็กเหมา ไม่ใช่มิเตอร์รายนาที

เทียบกับ imu.life ที่คิดเป็นเหรียญ/นาทีจริง ๆ (2–100 เหรียญ/นาที) — **เราไม่ทำแบบนั้น**

1. escrow ทำได้จริงเมื่อรู้ยอดตั้งแต่ต้น กันเงินก้อนเดียวตอนจอง
2. มิเตอร์รายนาทีต้องหักเงินระหว่างสาย ถ้าหักไม่สำเร็จตอนเน็ตสะดุดจะเถียงกันไม่จบว่าคุยไปกี่นาที
3. ผู้ใช้ที่เหรียญหมดกลางสายจะโดนตัดสายทันที ซึ่งแย่กว่าการรู้ตั้งแต่ต้นว่าได้กี่นาที

**แต่หน้ารายการแสดงราคาเป็น "เหรียญ/นาที"** ที่คำนวณจากแพ็กสั้นสุด เพื่อให้เทียบข้ามหมอดูได้เหมือน IMU

### call — เสียงเรียกเข้า

**v1 ดังเฉพาะตอนแอปเปิดอยู่** ผ่าน Realtime + เสียงในแอป · ไม่ทำ CallKit/PushKit
เพราะ VoIP push ต้องมีบัญชี Apple Developer ซึ่งยังไม่มี และ `push-sender` ยังไม่ได้เขียน

โมเดลนี้สอดคล้องกันเองกับสถานะออนไลน์: "Online = เปิดแอปอยู่" ซึ่งเป็นความจริงมากกว่า —
หมอดูที่ไม่ได้เปิดแอปกดรับสายไม่ได้อยู่แล้ว · เมื่อได้บัญชี Apple แล้วค่อยเติม CallKit
โดยไม่ต้องแก้ฝั่ง DB

### call — media

**LiveKit Cloud, เสียงอย่างเดียวก่อน** · `media_session.provider = 'livekit'`
· token ออกผ่าน Edge Function `media-token` ที่ตรวจว่า caller เป็นคู่สนทนาของสายที่ยัง non-terminal
· ไม่เก็บตัว JWT ลง DB เก็บแค่เวลาที่ออก token เพื่อ audit
· `call_kind` รองรับ `video` ไว้แล้วในสคีมา เปิดทีหลังได้โดยไม่ต้อง migration

### call — ledger

ใช้ผังบัญชีเดิมตาม §5.2 ไม่มีบัญชีใหม่:

| เหตุการณ์ | ขา | reference |
|---|---|---|
| จองสาย | `user_available −R`, `user_reserved +R` | `call_transaction`, id, `reserve` |
| เริ่มคุย | `user_reserved −R`, `seer_payable +share`, `platform_revenue +fee` | `call_transaction`, id, `settle` |
| ยกเลิก/ปฏิเสธ/หมดเวลา/ต่อไม่ติด | `user_reserved −R`, `user_available +R` | `call_transaction`, id, `refund` |
| ต่อเวลาครั้งที่ n | `user_available −E`, `seer_payable +share`, `platform_revenue +fee` | `call_extension`, id, `settle` |

การต่อเวลา**ไม่ผ่าน escrow** — จ่ายจบทันทีในทรานแซกชันเดียวกับที่ insert แถว `call_extension`
สำเร็จคือมีแถว ล้มเหลวคือไม่มีแถว

### ฝั่งแอป

- ต่อผ่าน seam เดิม `SupabaseHoroDataService` ตัวเดียว ไม่สร้าง client ชั้นใหม่
- Realtime ใช้ `ChataRealtime` ที่มีอยู่ เพิ่มช่องทางของ call เข้าไปในช่องเดิม
- สถานะสายในแอปต้องอ่านจาก `call_transaction` เป็นหลัก **Realtime เป็นแค่ตัวปลุกให้รีเฟรช**
  ไม่ใช่แหล่งความจริง — เพราะ `realtime.send()` ในทรานแซกชันคือ at-most-once ข้อความหายได้

## Testing Decisions

### เทสที่ดีในโปรเจกต์นี้แปลว่าอะไร

ตรวจ**พฤติกรรมที่มองเห็นจากภายนอก**เท่านั้น — ยอดเหรียญ สถานะ สิทธิ์การเข้าถึง —
ไม่ตรวจว่าโค้ดข้างในเรียงยังไง · และมีกฎที่ยึดมาตั้งแต่เฟส 3: **ของปลอมห้ามจำลองกฎเรื่องเงิน**
ความจริงเรื่องเงินมีที่เดียวคือ Postgres ของปลอมที่ฉลาดเกินไปทำให้เทสเขียวทั้งที่ระบบจริงพัง

### seam ที่จะเทส (ใช้ของเดิมทั้งหมด ไม่เพิ่ม seam ใหม่)

| ชั้น | ตอบคำถามว่า | ที่อยู่ | prior art |
|---|---|---|---|
| SQL | logic ในฐานถูกไหม | `db/tests/*.test.sql` | `money-flow.test.sql` — รูปแบบ "ตรวจยอดก่อน/หลัง + INVARIANT ต้องคืน 0 rows" |
| REST | contract ถูกไหมด้วยสิทธิ์ `authenticated` จริง | `scripts/test-rest-integration.sh` | ข้อ 5 (ครบวงจรเงิน) และข้อ 8 (verify-iap) |
| iOS | แอปคุยกับ Supabase ได้จริงไหม | `HoroTestTests/ChataAuthIntegrationTests.swift` | `testCancellingAnUnansweredQuestionRefundsEveryCoin` |

**ไม่มี seam ใหม่** — payout และ call เดินผ่านเส้นทางเดียวกับ question ทุกประการ
(RPC `SECURITY DEFINER` → PostgREST → `SupabaseHoroDataService`)

### สิ่งที่ต้องมีเทสแน่ ๆ

**payout**
- ถอนเกินยอดที่สุกแล้ว → ถูกปฏิเสธ และเหรียญไม่ขยับ
- ถอนขณะมีคำขอค้าง → ถูกปฏิเสธ (พิสูจน์ unique partial index)
- บัญชียัง `pending` → ถอนไม่ได้
- ขอถอนสำเร็จ → `payable_coin` ลดทันที และ ledger สมดุล
- ปฏิเสธ/ยกเลิก → เหรียญกลับมาครบ และมี reversing entry ไม่ใช่การ UPDATE ของเดิม
- รายได้ที่ยังไม่พ้น `hold_days` ไม่ถูกนับเข้ายอดถอนได้
- หมอดูคนอื่นอ่านคำขอของเราไม่เห็น (RLS ด้วยบัญชีที่สอง)
- ผู้ใช้ธรรมดาเรียก `admin_review_payout` → ถูกปฏิเสธ

**call**
- จองสาย → `available` ลด `reserved` เพิ่ม ผลรวมไม่เปลี่ยน
- โทรซ้อนขณะมีสายค้าง → ถูกปฏิเสธ
- หมอดูปฏิเสธ/หมดเวลา → เหรียญคืนครบ ไม่มีเศษค้าง
- เริ่มคุย → เงินออกจาก escrow เข้า `seer_payable` ตามส่วนแบ่ง และ `platform_revenue` ได้ส่วนที่เหลือ
- ต่อเวลาสำเร็จ → หักจาก `available` ตรง ไม่ผ่าน escrow
- ต่อเวลาโดยเหรียญไม่พอ → **ไม่มีแถว `call_extension` เกิดขึ้น** และเหรียญไม่ขยับ
- ยิง `extend_call` ซ้ำด้วย `sequence_no` เดิม → ไม่เกิดแถวซ้ำ ไม่หักเงินรอบสอง
- คนนอกขอ token จาก `media-token` ของสายที่ไม่ใช่ของตัวเอง → ถูกปฏิเสธ
- cron ปล่อย escrow ของสายที่ค้างเกินกำหนดได้จริง
- `ledger` สมดุลทุกธุรกรรมหลังเดินครบลูป

### สิ่งที่จะไม่เทสอัตโนมัติ

คุณภาพเสียงและการต่อ media จริงของ LiveKit — เทสได้แค่ว่า**ออก token ถูกคนและสถานะเปลี่ยนถูก**
ส่วนเสียงต้องทดสอบด้วยมือสองเครื่อง (มี `scripts/run-two-sims.sh` อยู่แล้ว)

## Out of Scope

- **Book Queue / นัดหมายล่วงหน้า** (domain `appointment`) — หมอดูออฟไลน์ให้ fallback ไปส่งคำถามข้อความ
- **CallKit / VoIP push / เสียงเรียกเข้าตอนแอปปิด** — รอบัญชี Apple Developer
- **วิดีโอคอล** — สคีมารองรับแล้ว แต่ไม่เปิดใน v1
- **PSP payout อัตโนมัติ** — โอนมือก่อน
- **admin app** — ใช้ Supabase Studio เรียก RPC
- **`moderation_action` / debt flag** เมื่อ Apple คืนเงินหลังถอนไปแล้ว — ยอมรับความเสี่ยงส่วนที่เหลือใน v1
- **ระบบ strike อัตโนมัติ** แบบที่ IMU ทำ (Warning → Strike 1–3 → Ban) — ควรมีในที่สุด แต่ไม่ใช่เฟสนี้
- **`seer_level`** — ยังใช้ `app_config.seer.default_revenue_share_bps` อัตราเดียวเหมือนเดิม
- **tip / ให้ของขวัญท้ายสาย**
- **บันทึกเสียงสาย**
- **Android**

## Further Notes

### ที่แกะมาจาก imu.life (คู่แข่งตรง)

- ราคา **2–100 เหรียญ/นาที** ตั้งโดยหมอดูเอง ไม่ใช่ราคากลาง
- สถานะ **Online / Offline** ชัดเจน ออฟไลน์เปลี่ยนปุ่มเป็น **Book Queue**
- คัดกรองด้วย: หมวดวิชา · ช่วงราคา · **ภาษา 6 ภาษา** · ด้านความแม่น · แท็บ Online Now / Top Rated / Video Call
- ป้าย **"✓ ยืนยันตัวตนแล้ว"** โชว์ให้ลูกค้าเห็น — KYC เป็นจุดขาย ไม่ใช่แค่ภาระ compliance
- ใช้ **recommends** ไม่ใช่ดาว 5 ระดับ
- ระดับหมอดู 5 ชั้น (Grand Oracle → Master → Rising Star → Apprentice → Novice)
  ตรงกับ `seer_level` ที่เราออกแบบไว้แต่ยังไม่ทำ
- นโยบายคืนเงิน: โอนคืนมือโดยแอดมินพร้อมเลขอ้างอิง เตือนเมื่อค้างเกิน 7 วัน ·
  คืนอัตโนมัติเมื่อหมอดูไม่ตอบใน 48 ชม. · **auto-strike สะสม 90 วัน โดยนับ "หายระหว่างดูดวงสด" เป็นความผิด**

สองอย่างสุดท้ายคือสิ่งที่เราจะเจอแน่นอนเมื่อเปิด call: หมอดูกดออนไลน์ไว้แล้วไม่รับสาย
สเปกนี้แก้ด้วย Presence ที่หายเองเมื่อปิดแอป แต่**ยังไม่มีบทลงโทษ** — ถ้าเปิดใช้จริงแล้วเจอปัญหานี้
ค่อยหยิบโมเดล strike มาทำ

### ความเสี่ยงที่รู้ตัว

- Realtime broadcast เป็น at-most-once — สายเรียกเข้าอาจไม่ถึงหมอดู ต้องมีการ poll สำรอง
  ตอนเปิดหน้าคิว ไม่พึ่ง broadcast อย่างเดียว
- pg_cron ละเอียดสุด 1 นาทีบนบางเวอร์ชัน แต่ `reservation_expires_at` ต้องการความละเอียดระดับวินาที
  → ให้ RPC ตรวจเงื่อนไขหมดอายุเองตอนถูกเรียกด้วย ไม่รอ cron อย่างเดียว
- LiveKit free tier มีเพดาน — ต้องดูโควตาก่อนเปิดให้ผู้ใช้จริง
